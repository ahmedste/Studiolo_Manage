0. In short

The owner's direction (28 Oct): questions and goals early; boards at the end; one actual prototype showing how Objects, boards, and questions and goals fit together.

Three systems, one idea each:

  1. An Object hosts questions and goals. "What I took from it" and its margin notes take @question and @goal, as notes do. Its card shows "? 2 · ◎ 1".
  2. A question can be answered in an Object. Answered in links to the case, building or drug that answers it. The Object's page then shows Answers: the questions it answered.
  3. A board's goal is a goal inline, and its questions are question inlines. They appear in the same Questions and goals list as every other question, named by their board.
  4. A board places Objects with their facts. An Object card on the canvas shows its card fields and its "? · ◎" counts, and opens the Object's page.
  5. Arrows and relation fields meet, but never merge. An arrow stays the board's claim (word and why). When an arrow joins two Objects whose collections have a matching relation field, the arrow offers one tap: Keep as a field ("Set New Gourna's Architect to Hassan Fathy"). Relation fields already set between two placed Objects show as faint dashed field links.
  6. An arrow into a question can answer it. An arrow with the word explains from a card into a question card offers Mark answered in Robinson? One tap; never automatic.

Why questions and goals come first. Q1 needs no migration: the words live in the note's own text, so learners start the habit on day one, and every later lane reads what they wrote. Q2 and Q3 run beside the field work in Stage 1. By the time Objects get relation fields (Stage 2), Answered in already exists for them to join.

Why boards come last. A board is where everything else is placed. It needs the photo roadmap's header, viewer and Picks (Boards design §1); question and goal inlines (Q2), so its goal and questions are inlines from the start and nothing is migrated twice; and relation fields (F2), so Keep as a field and field links work. Building it earlier means building its own goal field and question notes and then replacing them, which Boards design §0 and IN-D7 already ruled out.

Two agents, then three.

  • Agent A: Q1 → Q2 → Q4 → Q-O → Q5 → Q-B.
  • Agent B: F0 → F1 → F2 → F3.
  • Agent C (from Stage 1): P0 → P1 → V1 → P2 → V2.
  • Agent D (from Stage 1, after Q1 merges): N1 → N2 → C4 → N3 → N4.
  • Agent E (from Stage 1, beside Agent B): C1 → C2 → C3.
  • The small T phases slot in wherever an agent waits for a migration approval. Lane B starts after Stage 2 and the photo roadmap's Phase 7, and is one agent's lane from then on.

Migrations are numbered at merge. Each lane owns its tables (Q: item_inlines, inline_answers; F: collection_fields, item_field_values, content_relations.field_id; P: collections.page_layout; V: library_views; T: collections.base checks, collections.sensitivity; B: board_placements, board_arrows, board_frames, the board shape). 9. What this is not

  • Not a task manager: no assignees, due-date alarms or statuses beyond the ones above.
  • Not a database builder: no formulas or automations.
  • Not a whiteboard: no freehand, shapes or elbow connectors (Boards §5).
  • Not shared: boards, objects and questions are the learner's own in this programme.

3. Rules every phase keeps

  1. 2H stays true. An Object is in exactly one collection; a collection has one type; fields belong to collections; no folders. A field's type stays locked once it has values; removing a field retires it.
  2. One descriptor, as H14 did for kinds. Every field-type decision (editor, card text, table cell, sort, how Loci reads it) goes through field-types.ts (new, F0). No switch (valueType) outside it.
  3. Each lane owns its tables. F: collection_fields, item_field_values, content_relations.field_id. P: collections.page_layout. V: library_views. T: collections.base checks and collections.sensitivity. Two lanes never change the same column.
  4. Migration numbers are given at merge. Parallel branches name their migration 00xx_<lane>_<what>.sql and take the next number when they merge into main (and on the production cutover list), so branches don't fight over 0027.
  5. Hosted code never runs ahead of the hosted database (AGENTS.md). A phase with a migration merges only after the owner approves the migration and it's applied.
  6. The read path doesn't grow per card. Values stay in the one = ANY read; choice options and page layouts come with the collection fields already read once; anything shown only on an item page (the other side of relation fields) is one query on that page, never on the wall.
  7. The prototype design stays. New controls reuse what exists: rail rows (.prop), type pills (.coll-select-pills), the shelf tabs, the customizer's form rows and live preview, mcard cards.

F2 · Relation fields and 24 fields in groups.

  • Relation (relation) replaces the item type for new fields. Settings: which collection (or any item), one or several, and the name on the other side ("Cited by"). Values are stored as content_relations rows with a new nullable field_id and relation name field, so backlinks, Shelves threads and the graph see them with no extra read. Today's item fields keep working; the customizer offers "Turn into a relation" which copies item_value into a relation row.
  • The other side shows itself. On the target's page a block "Cited by (3)" lists the items whose relation field points at it: one query per item page (WHERE account_id = $1 AND to_item_id = $2 AND field_id IS NOT NULL, served by content_relations_account_to_idx).
  • Symmetric relation fields ("Alternatives") store one row with the lower id first, as see_also does.
  • 24 active fields, each in an optional group (collection_fields.group_name, ≤ 40). Groups become headings in the rail and in Table's column picker. Card fields stay ≤ 3.
  • Relation cap. Field links count toward the 5,000 per account (MAX_RELATIONS_PER_ACCOUNT). Raise it to 20,000 in the same phase, or keep field links out of the count: decision OB-D9.

F3 · Bases. base adds group (a firm, court, hospital), place (a site; a Place field leads its card) and event (a hearing, a procedure; a Date field leads and Timeline is its default view). Checks on collections and content_items widen; existing values are untouched. The base stays fixed after creation (2H P2).

2. Rules for every phase

  • The syntax is one paragraph, the same everywhere. A paragraph whose first word is @question or @goal (any case, followed by a space) is one inline; the rest of the paragraph is its words. In plain notes a paragraph is a run of lines between blank lines; in long notes it is a Markdown paragraph. \@goal writes the word literally. Only those two full words count, so an email address or a future @mention never turns into a question by accident.
  • Hosts: short notes, long notes and margin notes (any shape = 'note' with style plain or long, with or without about_id). Not quotes (a quote is the exact quoted text), and not Source descriptions or Object fields. These can come later (RQ-D2).
  • Never on the wall on its own. An inline shows through its note: on the note's card and page, and, for a margin note, on the parent item's card, as search already does.
  • Learner's words, learner's status. Loci never writes a marker or changes a status (Q5 only offers, with one tap, A2).
  • One parser. New src/features/library/inlines.ts :: parseInlines(body, style) returns { kind, text, position, due? }[]. It is pure and unit-tested, and the card builder, search, the save hook and the views all use it. Markdown's parseMarkdown gains two block types, question and goal, that call it.
  • Looks: questions use ? in --pick; goals use ◎ in --accent-soft (the colours the Boards design chose). No new tokens. Specimens go in src/dev/library-specimens.tsx, with screenshots at 1440 × 900 and 390 × 844, in light and dark.
  • Accessibility: a marked line is read as "Question: …" / "Learning goal: …" (visually hidden prefix). The @ menu works like the / menu, with arrows, Enter and Escape.
  • Paperwork and merging: as in the photos roadmap §2. A phase spec in studiolo/docs/superpowers/specs/ with its tier on line one; library.md, frontend.md, backend.md and database.md updated on the same branch; migrations hand-written and applied only on the owner's word; nothing merged before the owner has tested it.

0. In short

The owner's idea: a question or a learning goal isn't an item of its own. It's something you write inside whatever you're already doing. While writing a note you type @goal I want to understand how a deep court stays cool. While watching a lecture at 12:40 you type @question Why does the air move at night? into a margin note. On a board you drop a question between two cards. A question isn't a card on the wall. It lives in the note, the margin note or the board where it was asked.

So Commonplace gets a layer under the two it has:

The first three describe what you have. The inside layer describes what you want: what you're asking and what you're aiming for. That is exactly what Loci has lacked. Rules that keep it simple:

  1. Never on the wall on its own. An inline only appears through its host: as a chip on the host, a small "? 2 · ◎ 1" in the host card's foot, and in lists that always name the host.
  2. Your words, your status. Only the learner writes an inline or changes its status. Loci can offer one ("Make this a question?"), and that offer is an addition with one tap (A2), never a silent edit of your note.
  3. One question, everywhere. A question on a board, in a margin note or in a project is the same kind of thing, with the same chip, statuses and actions.

2.2 Typing it

  • @ at a line start or after a space opens a small menu, like today's / menu (slash.ts): Question (?) and Learning goal (◎). Typing @q or @g and Enter is enough.
  • It inserts a marker at the start of the paragraph: @question or @goal . The rest of the paragraph is the inline's words. In the textarea that reads naturally:

```markdown The court at Sultan Hassan stays shaded most of the day.

@goal Understand how a deep court stays cool without machines, well enough to brief the engineer, by March

@question Does depth matter more than width? @question How much does evaporative cooling help in humid air? ```

  • In view mode each marker becomes a chip: ? Does depth matter more than width? · Open ▾, with the goal shown above its two questions.
  • Why a paragraph, not words mid-sentence: a question or a goal is a thought of its own. A paragraph is easy to parse, easy to see in the textarea, and it survives copy, export and the Markdown view. Mid-sentence inlines can come later if people ask for them (IN-D2).
  • Why @ and not /: / already formats (a heading, a list). @ makes a thing that lives beyond the text and shows up elsewhere. Later, @ can also mention a topic or an item (@Hassan Fathy), which would replace the rail-only Mentions (IN-D4).
  • No ids in the text. When the host is saved, a pure function, new reconcileInlines(previous, parsed), matches the inlines by kind and order, then by closeness of the words. A reworded question keeps its status and answer. A removed question that has an answer or links asks first: "Remove the question Does depth matter…? Its answer goes too. Undo is available."
  • Phones and touch: the editor's toolbar gets ? and ◎ buttons, which insert the marker.
  • Dictation (the Moonshine proposal): saying "question:" or "goal:" at the start of a sentence inserts the marker.

9. What this is not

  • Not a task manager. There are no assignees, priorities or reminders. A goal's date is a horizon, not a deadline alarm.
  • Not a new type. Nothing is added to the type row, and nothing is added to the wall but a small count on a host's card.
  • Not Loci's notes. Loci never writes questions or goals into your writing. It only offers, and you tap.

0. In short

The owner's direction (28 Oct): long notes should feel like Craft notes, where you can embed images, questions and goals, and write about an Object. A long note opens a page you edit in place. And the links between all of this must stay simple, for the code and for the learner: always clear where to go and what to do.

Two decisions carry the whole design:

  1. A long note is a page you write on, not a record you edit. Selecting words gives a small bar. Every block has a handle to move it or turn it into another kind. The same editor writes an Object's What I took from it and short notes, so there is one way to write everywhere.

2. The connection model

2.1 Three kinds, one home each

Mention. You name an entry while writing: @Hassan Fathy in a sentence, or the entry shown as a card. A mention is part of the text and comes from it: delete the words and the mention goes. It has no name and needs no dialog. On the other side it shows as Mentioned in, with the sentence it's in, so the learner sees why it was mentioned.

Property. A named fact about an entry, in its rail: a relation field (Architect, Cites, Recommends; F2) or one of the named links from the Link dialog (Compared with, Made by). Both sides show it in their rails under its own name (Works, Cited by), because it is part of what each entry is.

Arrow. A claim on one board, with a word and a why (Boards §2.1). It belongs to the board. The entry's page lists the board under On boards, saying how many arrows touch it there.

3. The long note page

3.1 Layout

  • A reading column, about 700 px, centred on the stage. The title is the app's title field (ip-title-field), large Newsreader. Under it is one quiet line: About (the entry it's about, if any), its topics, and a count ("3 entries · ◎ 1 · ? 2 · Saved as you type"). A rule separates it from the writing.

0. In short

2. Collections, redesigned

2.1 Principles

  1. Show, don't form. Every choice is made on a picture of your own entries, never on placeholders.
  2. One question at a time. Four tabs, each about one thing. Each tab has a stage (the picture) and a panel (the few choices for it).
  3. Edit from where you are. You rarely open the studio from a menu. Click a property's name on any page, Add a property, Edit collection on the wall, or Edit on a tile, and the studio opens at that spot.
  4. Safe by default. Changes autosave with Undo. Hide comes before delete. A destructive choice says how many entries it touches first ("3 buildings have a value here").
  5. The same for every field. Starters differ (buildings, cases, drugs), but the studio, the words and the steps never do.

4.4 Links of links: one step only

flowchart LR

  • Backlinks are one step. Fathy's page lists B, not A. A shows B, but it doesn't mention Fathy. To see further, Open in Loci shows the neighbourhood on the map. Commonplace never shows chains.
  • Cards are shallow. A card shows an entry's own title, fields, excerpt and counts, never the cards or images inside it. So a card can't open into a card, and nothing nests.
  • Loops are harmless. If A shows B and B shows A, each shows the other's card once. Both list each other under Appears in. Nothing recurses, because cards are shallow and backlinks are one step.
  • Boards don't chain either. A board placed on a board would be a card of a board: its cover, title and counts. The prototype doesn't offer it, and B1 can add it later.

0. In short

The owner's idea (24 Oct): an infinite board where people place a photo, a link, a video, a note, a course or a Lumen, draw arrows between them, write their learning goal, and think freely. The board lives in the graph, at an area, topic or sub-topic. It is a Commonplace item, it holds other Commonplace items, and it can be turned into a Lumen.

The proposal in one line: a board is a Commonplace entry of its own type. It sits beside Notes, Sources and Photos, and its page is a canvas. Every card on it is a placement of an existing entry, drawn with the wall's own card, and it opens in the same viewer. Arrows carry a word and a why. The board feeds Learn (Make a Lumen) and Loci (the goal, suggested links, open questions).

What a board is for. Its job is understanding: working a question through until you can state what you now know, toward a goal you wrote first ("Understand how to keep the prayer hall's courtyard cool without machines, well enough to brief the engineer").

  • Thinking is the activity, learning is the purpose, and work is often where it points. The sample board is all three: you think by arranging and connecting, you learn because the goal and the questions ask you to, and the brief to the engineer is the work it serves.
  • So the design leans to learning. The goal card comes first. An arrow asks for a word and a why. Questions are their own cards. Recall and Make a Lumen test and teach what is on it. Loci reads the goal.
  • It is not a moodboard or a task board. No columns, statuses, owners or due dates. A board in a Practice area (a project, a competition entry) is the same board with a work goal, not a separate mode.

An entry type, not a collection. A board sits on the wall and on the shelves like a photo, and it shows other entries, but it does not own them the way a folder or collection would:

  • every card is a pointer to an entry that stays where it is, with its own topics;
  • one photo can be on three boards;
  • deleting a board deletes only its placements, arrows, frames and goal.

That is why a board can live at one place on Loci while its cards keep theirs, and why it is just another Commonplace item in the Palace and on the Map (§2.2).

Five rules:

  1. Placed, never copied. A photo on a board is the photo. Its picks, topics and notes on details are the same everywhere, and a change on the board is a change in Commonplace.
  2. What you write is saved to Commonplace. A note or question written on a board becomes a Note, tagged with the board's place. A pasted link becomes a Source › Link.
  3. Only four things belong to the board alone: placements (where a card sits), arrows, frames and the goal.
  4. It inherits Commonplace's look. The header, cards, viewer, selection bar and pop-overs are the ones the photo roadmap builds, unchanged (§1).
  5. It drives the app, through four outlets:
    • Make a Lumen follows the arrows, and its pictures become the Lumen's picture shelf.
    • The goal is what Loci reads as why you're learning the place.
    • Arrows between topics become suggested links on the map.
    • Questions become the Lumen's check.

  • A board is an entry. It has a title, one place (an area, topic or sub-topic), a goal, and a pick. It shows up in search, Views, Picks and Group by like any other type.
  • A placement points at something; it never holds a copy. It can point at a Commonplace entry, a detail (a photo and one of its region notes), a Lumen, a course, one slide of a Lumen, a lecture's saved moment, a Loci topic, or another board. Removing a placement never deletes what it points at.
  • Unpacking places a course's parts, a Lumen's slides or a lecture's moments. Each one remembers its parent (a dotted line). Fold takes them back, except the ones you moved or connected.
  • An arrow has a word from a fixed list (leads to, explains, example of, contrasts with, causes, raises, part of) and an optional why of one line. The word lets Learn and Loci read it; the why is the learner's own sentence.
  • Writing on a board creates the Commonplace entry first, then places it.

2.1 What an arrow means

An arrow is a claim the learner makes about two things, on this board: A [word] B, because [why]. For example: "Courtyard house, aerial" example of "Courtyard toward the prayer hall", because "same court, but here the tall wing holds the tower".

  • It belongs to the board, not to the entries. The same two photos can be joined differently on another board, or not at all. The viewer's On this board shows only this board's arrows.
  • It is not a hyperlink, and not a link on the map. It never changes Loci by itself (below).
  • The word is for the app; the why is for the learner. The word comes from the fixed list so Learn and Loci can read it. The why is kept in the learner's own words, quoted back by the Lumen, and covered by Recall.

2.2 How a board lives in Loci

A board is a Commonplace item, so the Palace and the Map treat it as they treat a photo or a note. Nothing about the Palace or the Map changes shape. A board only brings its own card and, when opened, its own satellites.

  • Its place. A board's one place is its topic (content_items topics, as for any item). In the Palace, its area's room counts it in the Commonplace stack (stack:commonplace:<area>, room.ts), newest first, beside the photos and notes.
  • Opened in the Palace (item:<id>, the slot card on the right):
    • the board's square sits near its topic and serves it, as any item serves its topics;
    • its cards appear as small marks near their own topics, held by the board (holds, not drawn) and serving those topics, so you see where the board reaches across the map. A Loci topic placed on the board is tied to the board directly;
    • its arrows are drawn between them as related links carrying the why;
    • Lumens made from it are tied to it (serves), exactly as the app already ties a Lumen anchored to an item (extras.ts: anchor.kind === "item").
  • Its slot card reads Commonplace · Board: the cover, the goal, Lives at, Reaches, through what's on it, On it, Its arrows (as sentences), Lumens made from it, then Open board and Open in your Commonplace →.
  • On the Map, the topic's Commonplace lane lists the board first with its cover and the kind line BOARD.
    • A Lumen made from the board appears in the Lumens lane as From board, because its anchor is the board (an item).
    • The board's lane card gets the ▶ badge: 1 Lumen made from Cooling the prayer-hall courtyard, with the app's own peek and Play. This is the lane's existing itemCounts, keyed by the board's id (topic-gateway.ts).
  • The explainer link is the existing one. A Lumen made from a board is anchored to the board as an item. Learn, the Map lane, the badge and the Palace already read that anchor, so the board joins all of them without new plumbing.
  • What is new for Loci is the item kind board (its label and lane card, in item-kinds.ts), the satellites for an opened board, and the inspector's Boards section (B4).

3. The phases

B1. Boards as entries (HIGH, migration)

Goal: a learner can make a board at a place, put their own things on it, connect them and say why.

  • The type. Boards in the type row, the slim bar (§1), the wall card with its cover, the Boards shelf.
  • Making one. + New board on the Boards slim bar, or New board here from a topic (B4 adds that one). It opens with the goal card waiting to be written.
  • The canvas.
    • Drag on empty space to pan; Ctrl/⌘ + scroll or pinch to zoom; the minimap; Fit (0).
    • Tools: Select (V), Pan (H), Note (N), Question (Q), Arrow (A), Frame (F). Double-click empty space for a note.
    • Shift-drag a box to select several.
  • Placing. The drawer (§1). Drop where you let go; a tap places it at the nearest free spot. Pasting a link saves it as a Source first.
  • Arrows. Drag a card's edge dot onto another card (or press A, then tap two cards), then pick a word and say why. Dropping the dot on empty canvas makes a new note that's already connected.
  • Writing. Double-click a note to edit it. It saves to Commonplace, and the toast says so.
  • Keys and undo. Delete removes from the board. Ctrl/⌘ Z undoes board changes.
  • Done when:
    • a board made, filled and connected shows its cover on the wall and shelf;
    • a note edited on a board reads the same in Commonplace;
    • removing a photo from a board leaves it on the wall;
    • the board works at 390 px with the bottom bar, in light and dark;
    • every tool and card is reachable by keyboard.

B2. The board and the viewer (MEDIUM, no migration)

Goal: a board is a way into the pictures, not a second place to look at them.

  • The viewer. Double-click or Space on a photo opens the Phase 2 viewer. Its list is the board's photos in arrow order, so ← → walks the board's argument.
  • The viewer's panel adds:
    • On boards: each board that holds the photo, with this board marked;
    • On this board: the arrows as sentences, e.g. "Courtyard house, aerial example of Courtyard toward the prayer hall, because same court, but here the tall wing holds the tower."
  • Details. Each note on a detail gets Place detail N on the board, which adds a detail card linked to its photo by part of.
  • Lectures. A lecture unpacks into its saved moments.
  • Done when: ← → in the viewer follows the arrows; a placed detail shows its region box at any zoom; closing the viewer returns to the board exactly where it was.

B3. Learn on a board (HIGH, migration: a Lumen's source)

Goal: the board is the brief for a Lumen, and a place to test yourself.

Lumens and courses as cards. A Lumen card plays in place and unpacks into its slides. A course card shows its progress and unpacks into its parts (each part is a Lumen).

Make a Lumen, from the whole board, a frame or a selection:

  • The brief. The goal is the brief. The level comes from what Loci knows about the place.
  • The picture shelf (Lumen pictures) is the board's own photos and detail crops, in arrow order. Each one is Use or Leave out, and the learner chooses When nothing of yours fits: Ask · Generate · Words only.
  • The order. Follow my arrows (the default) or Let Loci order it. Frames become sections; with A course, each frame is one part.
  • The writing.
    • The arrows' whys are quoted in the learner's words.
    • Two connected cards where at least one is a picture become a photo_pair slide, with the word between them.
    • Lumens and courses on the board are context the new Lumen builds on, not repeats.
  • The check. Questions become the check at the end, answered after the learner tries. Afterwards each question card shows Answered in "…".
  • Length. Connected cards (the default) leaves out anything with no arrow; Everything keeps them all.
  • Where it lands. The Lumen appears on the board, linked to its frames by dashed arrows. It is also in Learn.

Recall covers the learner's own words: notes, quotes, the goal, detail notes, and each arrow's word and why. Say one aloud, tap to check, then mark Got it or Not yet. Not yet goes to To revisit in Loci's memory for the place.

Ask Loci works on a selection, and you go first:

  1. Loci asks What connects these?
  2. You write a sentence, then Compare.
  3. Loci shows its version next to yours. You keep yours, theirs, or both as notes; it can also offer to place a topic.
  4. Nothing is added without a tap. Just tell me skips your turn.

Data. A Lumen records its source board, frame or selection, so the board can show it and Learn can say where it came from.

Done when:

  • a Lumen made from the sample board follows its arrows, uses its pictures, and quotes its whys;
  • each question gets a check;
  • the words-only fallback works with every picture left out.

B4. Boards in Loci (HIGH, migration: topic links)

Goal: a board changes what the map knows.

  • In the Palace and on the Map, as §2.2: the board is a Commonplace item in its area's stack and its topic's lane. Opened, it shows its cards near their own topics, its arrows as related links with their whys, and the Lumens made from it. The Map's lane card carries the ▶ badge for those Lumens.
  • In the inspector (Phase 7), a Boards section:
    • the boards' covers as tiles, and + New board here;
    • Loci reads: the goal of the board placed at this topic, shown as why you're learning it;
    • From your boards: when an arrow joins two topics the map doesn't link, the inspector suggests the link and shows the arrow that implies it, with Link them or Not now;
    • Open questions on boards, each with Explain….
  • Which arrows count. An arrow into the board's own topic, or between a topic and one of its own parents, never suggests anything.
  • Done when:
    • a new board shows in its area's Commonplace stack and its topic's lane, with no change to how other items show;
    • opening it in the Palace places its cards near their own topics and never moves a topic (the Palace's rule C-17);
    • a Lumen made from it shows From board in the Lumens lane and the ▶ badge on the board's card;
    • linking from a suggestion adds the link to the map, and Not now never asks again for that pair;
    • the goal appears in the place's memory card under Why you're learning it (learner memory §4);
    • Explain… starts a short Lumen whose check is that question.

5. Not in this programme

  • Shared or live boards, comments, or several people on one board.
  • Drawing freehand, shapes or connectors with elbows. Arrows are straight; frames are boxes.
