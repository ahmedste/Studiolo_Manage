Part 1

Proposal: better Lumens, and where the board fits

Status: review and plan, for the owner's decision · 19 Oct 2026 Builds on: 2026-10-19-lumen-board-sketching.md and the board prototype Prototype for this plan: prototypes/lumen-board/. It mocks the real player, Learn, Library and Explain dialog, and the copilot, with a Today / Proposed switch covering §4.2, the board slide (§5.2), the dialog hint, copilot offer, Draw it short and course-part hint (§5.3, §5.5), and posters. Evidence: studiolo @ c7d39da (main, 19 Oct; read only), its run evidence and specs, and the Craft Studilo space (read only).

1. Summary

Lumens work, but they are short, visually static and checked mostly by the prompt itself.

  • Length. The 40 tuned runs (AI tune-up, run 3) have a median of 315 narration words, about 2.0 minutes. 17 of 40 are under 2 minutes, none reach 3, and none has more than 8 slides. The contract asks for 2–6 minutes, "most near the middle", and 6–12 slides.
  • Visuals. They are the weakest-scored dimension. The judge's means are visual use 3.13 and visual polish 3.10, against 3.9–4.0 for accuracy, story, clarity and pacing. 139 of 211 recorded faults are visual: empty halves of the frame, scenes that haven't started, and diagrams that look like stock Mermaid.
  • Static slides. Eight of the eleven slide types appear all at once, and the voice never builds them. Only infographics and animations move with the narration.
  • Untested promises. Several contract rules have no check behind them: the length floor, the answer-slide type, "every slide has a say", and counts that must match the screen. Warnings are never sent to repair.

The board fits as one more slide type written in the same author pass. Every creation path ends in the same function (generateQuick), so adding it to the contract and ingest makes it available to the topic Explain button, library items, the copilot, course parts and onboarding at once. The paths only differ in whether they hint that a board would help. Boards also address three of the problems above: they build with the narration by nature, they fill the frame, and they break up the run of tables and animations.

Recommended order:

  1. Now: six small fixes that raise every Lumen (§4.1).
  2. Next: "build with the voice" for every typed slide (§4.2).
  3. Then: the board as a slide type with a light hint from each entry point (§5).
  4. Later: a short board-only "draw it for me" from the copilot (§5.5).

2. How a Lumen is made today (short version)

flowchart LR
  A[Topic Explain button] --> G
  B[Library item Explain] --> G
  C[Copilot offer card: Make it] --> G
  D[Course part opened] --> G
  E[Onboarding first Lumen] --> G
  G[generateQuick: gate, row, brief context] --> W[Trigger job runGenerate]
  W --> S[Sources: item text, BM25 when large]
  S --> P[Brief + cached contract 1.4]
  P --> O[Opus 5.5 low effort, streamed]
  O --> I[Ingest: validate each block]
  I --> R[Repair: reject tier only, 2 rounds]
  I --> V[Scene checks in QuickJS]
  I --> T[Speech: one ElevenLabs job per say]
  T --> PL[Player: draws slides live with word timings]
  • One entry point. generateQuick is the only one (src/features/explainers/service.ts:245-250, 278-411).
  • Brief. Depth is always "overview", and there is no length or format field (contract/brief.ts:57-59, 147-161, 196).
  • Models. The author is Opus 5.5 at low effort with 32k tokens; repair is Opus at medium (features/ai/purposes.ts:34-36).
  • Slide types. Only the author picks them, from contract §3 (contract/text.ts:52-70). No path hints at a type.
  • Copilot. The conversation never reaches the author: only the request and focus strings do (copilot/tools/explain.ts:17-42, prompt/system.ts:263-268).
  • Library items.
  • An item is grounded strict when its text can be read: PDF native text, a link, or a note or quote body.
  • Citations live only in narration. Item bodies may not carry them (text.ts:113, ingest/types.ts:50-62).

5. The board inside the system

5.1 Principles

  1. Same author, same pass. The lab found that splitting writer and drawer always loses quality (E25–27, Craft AI Lab & Test Results). The board is written by the explainer author inside the same stream as the narration, as data: one line per mark (see the prototype format). It is not code, so it needs no QuickJS sandbox.
  2. Same timing system. Narration refs already pin animation moments (ingest/refs.ts:113-123). A board uses the same refs: [[s4.cache]] starts drawing cache as the word is spoken, and a second ref points back at it.
  3. Same look. The board uses Studiolo's light and dark stage values and role colours, which the prototype now does. No pen is shown: a small ink dot does the drawing and stands in for the pointer.
  4. Grounded like everything else. Citations stay in narration. In strict mode, board labels are checked against the cited spans (§5.4).

It needs plumbing through GenerateQuickInput, fitJobInput, readBriefContext and the create-key check sameRequest, so that existing keys don't change (service.ts:184-205). It never goes into focus, which would pollute the stored request and break the copilot's no-added-framing rule.

5.4 Grounding and citations for boards

  • Today. A board mark is grounded only through the say that refs it. Citations attach to narration spans (refs.ts:243-277).
  • Proposed check, strict mode only. At ingest, every board label containing a number or a proper name must appear in a cited span or in the say that draws it. Otherwise it gets board_label_unsupported, a warning sent to repair. This stops a board from showing a figure the sources don't contain.
  • Viewer link (optional). A mark drawn in the same say as a citation could show that citation when tapped. Both carry offsets in the clean say text (ingest/types.ts:45, 62), so the link costs no extra model work.

5.5 A short board on its own ("Draw it for me")

A one-board answer in the copilot is attractive: a 30–60 second sketch with voice, for "how do these relate?".

  • What it would reuse: generateQuick, the gate, the job, ingest, speech, the player and citations.
  • What would be new:
  • A short mode of the contract: no intro, one board, 2–4 says and one follow-up. The contract currently requires an intro, 6–12 slides and two follow-ups (text.ts:76, 113, 247).
  • An embedded player in the copilot card.
  • A decision on where shorts live in Learn and whether they can be shared.
  • Cost and latency. My estimate is about US$0.02–0.05 and a first stroke within a few seconds; this is not measured. A short still takes one of the two-at-once slots.
  • Naming. "Sketch" is taken: the onboarding map uses it. Use "Draw it" or "Board" in the interface.
  • Sketch a highlighted passage. "Explain this" on a highlighted PDF passage was explicitly out of scope in 3B-4 (spec §12). The hook exists (library/select-to-quote.tsx:24-40): saving the selection as a quote already gives a strict-grounded note with a page. That makes it a natural second step once shorts exist.

5.6 When to use a board, a diagram or an animation (proposed contract wording)

  • Board: an idea explained by building a picture one piece at a time, in the order it is spoken: relationships between parties, a cause and its effect, a before and after, an annotated graph, a labelled section. The value is in the order of the build and in pointing back at parts.
  • Diagram: a flow, hierarchy or state machine whose final shape matters more than the order it was built in.
  • Animation: motion over time, or precise geometry, such as a plan, a section, load paths in 3D, or a growing quantity.
  • Mix. In a 6–10 slide Lumen, use at most two boards, and never two boards in a row.

5.7 How boards help the quality problems

Problem (§3) How a board helps
Static typed slides A board is drawn with the voice by nature
Empty halves of the frame Boards are laid out on the whole 1280×720 stage, and the checks flag empty or overflowing layouts
Run of tables and animations A third visual mode, cheap to render and with no sandbox
Scene stills with nothing happening yet A board starts drawing on the first ref; there is no blank first tenth to reject
Cost Boards are data, not code: no kit, no QuickJS run, and repairs are small

Part 2

Investigation: board slides for Lumen (sketching on a whiteboard)

Status: investigation and working prototype, for the owner's decision · 19 Oct 2026

Prototype: prototypes/lumen-board/ (open index.html in a browser; it also runs as a claude.ai artifact, where "Draw it with Claude" works). Since 20 Oct it mocks Studiolo's own Learn, player, Library and copilot screens; see 2026-10-19-lumen-quality-and-board-integration.md.

1. Summary

A board is a new kind of Lumen slide. A rough, coloured sketch is drawn on Studiolo's stage, in the app's usual light or dark theme, while the voice explains it, the way a person explains an idea at a whiteboard. Boxes, arrows, circles, handwritten labels, underlines and highlights appear as the voice says the word that names them. No pen or hand is shown: a small, plain dot of ink moves along each stroke as it is drawn. When the narration comes back to something already drawn, the dot goes back and rests on it.

The prototype shows this works with the pipeline Lumen already has:

  • The author model (Claude) writes a board as data, not code: one line per mark, such as cache box 540 420 200 110 emphasis hatch "Cache".
  • Narration uses the refs Lumen already has ([[b1.cache]] before a word) to say when each mark is drawn.
  • Word timings come from ElevenLabs with-timestamps, which studiolo already calls (src/features/explainers/speech/elevenlabs.ts).
  • Every frame is a pure function of the time t, like today's animation scenes. Seeking, stills, thumbnails, reduced motion and any later video export all work the same way.

Recommendation. Add board as an item type in contract 1.5, using the prototype's renderer as the starting point. Leave whiteboard libraries such as tldraw and Excalidraw out of the player. Use a small in-house renderer (about 700 lines) with two MIT/OFL pieces: perfect-freehand for marker strokes, and the EMS Tech single-line font for handwriting. Estimated effort: about 6–9 days (§8).

2. Where it fits in today's Lumen

References are to studiolo @ c7d39da (read only; nothing there was changed).

Today Board slide
Item types: intro, ul/ol, cards, table, code, diff, math, diagram (Mermaid), infographic, animation (JS scene) (src/features/explainers/ingest/items.ts) Adds board. Its body is a header, ---, then one mark per line. It is plain data with no code, so nothing has to run in the QuickJS sandbox.
A ref [[s5.rise]] pins an animation moment to a word and moves the pointer (contract/text.ts §4, player/timeline.ts pointerTarget) The same syntax. The first ref to a mark starts drawing it; a later ref sends the drawing dot back to point at it.
The pointer moves to an anchor leadWords ahead of the voice (player/stage/pointer.tsx) On a board slide the drawing dot is the pointer. It draws, fades when the board is quiet, and comes back to rest on a mark the voice names again.
An animation scene is draw(s, t, k), a pure function of t (scene/runtime.ts) A board is also a pure function of t: marks + schedule → frame(t).
Diagram slides are Mermaid, and the contract says "never imitate a drawing with a diagram" Boards cover the space between the two: an explained sketch with spatial layout and annotation, with no code for the author to write.
Role colours: emphasis, second, third, fourth, neutral, ink (scene/role-palette.ts) The same role names and the same light and dark values (colour set "series", stage surface --surface-panel), so the contract's "roles" legend line and colour rules carry over and boards follow the app theme like every other slide.
ElevenLabs with-timestamps gives word timings, with estimated timings as the fallback (speech/elevenlabs.ts, speech-estimate.ts) The prototype estimates timings at 160 wpm. In the app the real word timings slot straight in (§6).

  • Board: an idea explained by building a picture one piece at a time, such as a mechanism, a cause and its effect, a before/after, a worked sketch or an annotated graph. The value is in the order of the build and in pointing back at parts.
  • Diagram: a flow, hierarchy or state machine whose shape matters more than the order it is built in.
  • Animation: motion over time, or a precise spatial or 3D drawing.

3.2 Handwriting the labels

To write text stroke by stroke you need single-line fonts, whose glyphs are pen paths rather than filled outlines.

  • EMS Tech (Hershey/EMS set in the hersheytext npm package, MIT; the font itself is SIL OFL). It is a single-line version of Architects Daughter, an architect's hand, which suits Studiolo's audience. Used in the prototype: 95 ASCII glyphs, about 10 KB of stroke data.
  • Tegaki (kurtgokhan/tegaki, MIT): stroke-by-stroke handwriting from any font, with harfbuzz shaping, so Arabic and right-to-left text work. It is the upgrade path if Lumen needs non-Latin labels.
  • Relief SingleLine (OFL): a cleaner technical-pen style.
  • Fallback approach: a handwriting outline font (Caveat, Kalam, Excalifont) revealed with a left-to-right wipe. It is cheaper but looks less like real writing.

3.3 Getting an LLM to produce diagrams

  • The most reliable pattern is structured data with coordinates (a DSL or Excalidraw skeleton JSON) that a renderer checks and draws. Asking the model for raw SVG tends to break the layout. Asking it for code is what animation scenes already do, at the cost of the sandbox and repair loops.
  • Prior art: Excalidraw's AI diagrams go through Mermaid; cristianodabc/narrated-explainers (MIT) has the LLM write a story JSON that is rendered to SVG and video. Its "data only, never code" rule is the right security model for boards as well.
  • No academic paper turned up on LLM-generated whiteboard explainers specifically.

3.4 Syncing to the voice

  • ElevenLabs POST /v1/text-to-speech/{voice}/with-timestamps returns per-character times. Studiolo already turns these into word timings (alignmentToWords). POST /v1/forced-alignment exists for audio made elsewhere.
  • The pattern: strip the [[…]] refs before speech, keep their character offsets, map each offset to a word's start time, then schedule the drawing from those times. Drive the frame from the audio clock, never from timers.

3.5 Existing skills and MCP servers

  • excalidraw/excalidraw-mcp (official, MIT): Claude draws Excalidraw diagrams in chat.
  • yctimlin/mcp_excalidraw: an MCP server for a live canvas, plus a Claude Code skill.
  • Excalidraw diagram skills: coleam00/excalidraw-diagram-skill (renders with Playwright so the agent can check its own drawing), garrytan/gstack diagram (recommends at most 15 nodes per scene), axtonliu/excalidraw-diagram, and awesome-copilot's excalidraw-diagram-generator.
  • anthropics/skills has no whiteboard or Excalidraw skill. The user's claude.ai skill catalogue returned nothing for whiteboard, Excalidraw, sketch or tldraw.
  • None of these produce narrated, time-synced drawing. They are useful as references for prompting and for the self-check loop.

3.6 Exporting video (if Lumens are ever downloaded as MP4)

  • Remotion 4.x renders React frames as a pure function of the frame number. It fits a board component directly. Free for teams of up to 3; company licence above that (via search).
  • Free alternative: headless Chromium with a virtual clock (puppeteer-capture), then FFmpeg to mux in the narration MP3.
  • Motion Canvas (MIT) works but would be a second rendering stack.

4. The prototype

prototypes/lumen-board/index.html is a single page with no build step. It loads perfect-freehand from jsDelivr and falls back to plain round strokes if that fails; the font data is inline. Since 20 Oct 2026 it is styled from studiolo @ 4b4ee63 (tokens, explainer, copilot, graph and shell CSS), so boards appear inside Studiolo's own screens.

What it does:

  • Learn: Lumen cards. Posters show a finished board under the proposed player.
  • Player: the real stage, title card, list, table and cards slides, cursor, captions, controls, and the Transcript and Slides panel, plus board slides drawn by the ink dot.
  • A Today / Proposed switch compares the current player with the proposed changes in the quality plan.
  • Three full Lumens in the author's markup, chosen to see whether one format covers different fields:
  • Who is bound to whom (contracts, from a library PDF, with page citations and a General knowledge run): the parties, the web of contracts drawn as each is named, the missing client–subcontractor link, the collateral warranty, and an answer board.
  • Reading a building section (architecture): a section drawn from the ground up, then the stack effect.
  • Where the eye goes (graphic design): the rule of thirds, the four levers of hierarchy, and a poster with its reading order numbered.
  • Library: the Explain dialog with a proposed "Draw it as it explains" hint.
  • Copilot: an offer card with a sketch hint, an inline Draw it short (one board, about 30 s), and a course plan with parts marked to be drawn.
  • Board lab: edit any Lumen's markup and play it, with checks. Draw it with Claude writes a new board from an idea (the prompt is the page's SPEC, a first draft of the contract section).
  • Narration: the speaker button reads aloud with the browser's own voice, as a stand-in for ElevenLabs. The clock re-syncs on word-boundary events.
  • Reduced motion and keys: reduced motion shows finished marks with no drawing dot. Keys are Space, ← →, J/L, C, and , and . to step between slides.

4.1 The board format (draft)

<item id="b1" type="board" title="Why a cache makes reads fast">
roles: fourth = the slow trip; third = the fast trip
---
app    box 120 250 200 110 ink "App"
db     cyl 960 220 200 170 ink "Database"
slow   arrow app db fourth bend 0.22 "every read: ~80 ms"
cache  box 540 420 200 110 emphasis hatch "Cache"
check  arrow app cache emphasis "ask first"
hit    ring cache third
</item>
<say>Suppose your [[b1.app]]app needs the same record again and again. Each time it goes to the [[b1.db]]database, and that [[b1.slow]]round trip costs around eighty milliseconds.</say>
<say>So we put a small, fast store in between: a [[b1.cache]]cache. Now the app [[b1.check]]asks the cache first, and every later read is a [[b1.hit]]hit.</say>
  • Shapes: box, circle, ellipse, diamond, poly (a closed outline such as a roof or a building), cyl, person, text, arrow, line, curve, axes, ground.
  • Annotations: underline, ring, highlight, cross, tick.
  • Options: a colour role; hatch, dash, arrow, bend n, small, big, title, size n, center; a quoted label.
  • Positions: on the 1280 × 720 stage, inside the safe area x 64–1216, y 64–600. These are the same numbers as the scene contract.
  • Arrow ends: an id or a point. An arrow between two marks attaches to their outlines automatically.

4.2 How a frame is made

  1. Parse the source into mark specs. Ids must be declared before they are referenced, the same rule as refs.
  2. Build each mark's centrelines. The wobble is seeded from boardId:markId, so a mark looks the same on every render. Labels are written with the single-line font, and each mark records its box, outline, anchor and stroke lengths.
  3. Time the words. The prototype estimates them; the app will use measured timings. A ref's time is the start of its word.
  4. Schedule the drawing. - A mark starts 140 ms before its word. A mark with no ref follows the mark declared before it, and a mark never starts before the marks it connects. - Drawing time comes from stroke length divided by drawing speed: shapes about 900 px/s, handwriting 560 px/s, hatching 2,400 px/s. It is squeezed to as little as 40% when the next cue is close. - The dot travels between marks at about 1,900 px/s, plus small lifts between strokes. - A later ref to a mark already drawn becomes a "point" event when the dot is free.
  5. Draw at t. Finished strokes are cached as Path2D and only the stroke in progress is recomputed each frame. Then the drawing dot is drawn in the ink's colour. It is a plain dot with no glow or shadow (about 8 px across on the 1280 px stage while drawing), smaller and fainter while moving between marks, and it fades out about a second after the board goes quiet. No pen, hand or eraser is shown. Between boards a soft wipe clears the old board and leaves a faint ghost, the way a real whiteboard does.

4.3 How it was checked

  • The page was rendered in headless Chromium on every screen, at the end of boards and part-way through, under Today and Proposed, in light and dark, and at 390 px width.
  • There were no console errors, all examples report "No problems found", and the page has no horizontal scroll at phone width.
  • While the new examples were being written, the checker caught two mark ids that clash with option words (center and big) and a label running past the drawing area. The contract should list the reserved words, and these checks belong in the repair loop.
  • Screenshots from that run were used to adjust label placement, text size and the layout of the examples.
  • Not yet tried: how reliably Claude follows the format. "Sketch with Claude" is wired up, but nobody has run a set of topics through it yet (§7).

5. Limits of the prototype

  • Narration timing is estimated; the browser voice is a stand-in for ElevenLabs.
  • The handwriting covers ASCII only (EMS Tech): no Arabic or other scripts. Tegaki is the route to them.
  • Layout is entirely the author's coordinates. There is no auto-layout, so a careless board can overlap. The checker warns about overlaps but doesn't fix them.
  • Hatching is only clean on convex shapes: box, circle, ellipse, diamond and the body of a cylinder.
  • There is no undo, no learner editing, and no MP4 export.
